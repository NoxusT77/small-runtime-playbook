# 5 Object Storage Rules for SaaS User Avatar Uploads and Resident Files

TL;DR: The simplest object storage choice is the one that keeps application servers out of the file path while preserving authorization at both ends. For a property-management SaaS handling resident photos, inspection videos, and lease attachments, large-file throughput makes that constraint decisive: issue short-lived upload and download capabilities from the backend, use multipart uploads for large objects, and keep the bucket private. Do not choose from an S3-compatible checkbox alone. Test the exact signing, CORS, multipart, expiration, and cleanup behavior your workflow needs.

A signed URL is a temporary capability, not a replacement for application authorization. The backend should decide which tenant and user may act, bind that decision to a narrowly scoped object key, and then let the client move bytes directly to or from storage. This also keeps retry traffic away from the application process, where an interrupted inspection-video upload could otherwise compete with leases, maintenance requests, and notifications.

## 1. How should SaaS object storage handle user avatar uploads?

Proxying every upload through the API looks simple because authentication and file transfer occupy one request. Under large-file concurrency, it couples web-worker capacity, request timeouts, memory pressure, and deployment restarts to the duration of each transfer. A direct-to-storage flow leaves the API responsible for policy and metadata rather than sustained byte transport.

The useful boundary is small: the client asks to start an upload, the backend authenticates the resident or property manager and chooses a tenant-scoped key, and storage accepts the bytes through a signed capability. Downloads follow the same pattern after a fresh authorization check. **Private-by-default storage plus short-lived capabilities is the baseline**, not an optional hardening pass.

That boundary matters.

Keep avatar handling on the same policy boundary, but do not let its small typical size define the whole system. Property records can include much larger media. The storage evaluation should therefore exercise both a small image and a deliberately interrupted multipart transfer, rather than declaring success after one tiny upload.

## 2. Make multipart behavior part of the selection test

Multipart upload divides one object into independently uploaded parts. The S3 documentation notes that failed parts can be retransmitted without restarting the entire object, and that parts can be uploaded independently and in parallel. Those properties matter more for a large inspection video on an unreliable connection than they do for a profile image.

Retries happen.

There is a catch. After a multipart upload begins, uploaded parts continue to consume storage until the upload is completed or aborted. A crashed client cannot be allowed to create an indefinite trail of unfinished work. The design needs a durable upload record, an explicit completion step, and a cleanup process for abandoned upload sessions.

Treat concurrency as a measured control. More parallel parts may improve throughput, but they also create more simultaneous requests and can worsen contention on constrained client networks. Start with a conservative client setting, record part latency and retry counts, then adjust using production-shaped tests. No universal concurrency number follows from the protocol.

## 3. Sign policy decisions rather than trusting object names

Object keys should be generated by the backend and scoped to a tenant, record, and opaque file identifier. Never accept a complete storage key from the browser and then sign it unchecked. A resident who can alter a property identifier in a request must still fail the backend authorization check before any signed URL exists.

A small interface makes that responsibility visible without tying business logic to one SDK:

```python
from dataclasses import dataclass
from datetime import timedelta
from typing import Protocol


@dataclass(frozen=True)
class UploadGrant:
    object_key: str
    url: str
    expires_in: timedelta


class ObjectSigner(Protocol):
    def sign_upload(
        self, *, object_key: str, content_type: str, expires_in: timedelta
    ) -> UploadGrant: ...

    def sign_download(
        self, *, object_key: str, expires_in: timedelta
    ) -> str: ...


def grant_resident_upload(
    *, tenant_id: str, resident_id: str, file_id: str,
    content_type: str, signer: ObjectSigner
) -> UploadGrant:
    allowed_types = {"image/jpeg", "image/png", "application/pdf"}
    if content_type not in allowed_types:
        raise ValueError("unsupported content type")

    object_key = f"tenants/{tenant_id}/residents/{resident_id}/{file_id}"
    return signer.sign_upload(
        object_key=object_key,
        content_type=content_type,
        expires_in=timedelta(minutes=10),
    )
```

This example fixes a ten-minute policy for illustration; it does not claim that ten minutes fits every deployment. The real value should cover expected transfer startup and retry behavior without leaving a capability useful longer than necessary. Large uploads also need a distinction between the lifetime of authorization to start or sign parts and the time required to finish the multipart session. Verify those semantics against the implementation under evaluation.

Ten minutes is a policy choice.

Treat client-supplied media types as claims. Validate the completed object before making it available to other users or downstream processors, and store authorization-relevant metadata in the application database rather than relying on a key prefix as the only access model.

## 4. Test browser policy and failure states together

CORS is enforced by browsers for cross-origin requests. Some requests trigger a preflight, and the server must answer with the appropriate access-control headers. A successful command-line upload therefore does not prove that the browser path works. Test the deployed web origin, the actual method and headers, and both preflight and transfer responses.

Keep the allowed origins and headers narrow enough to match the application. CORS is not authentication; it controls which browser origins may read responses, while the signed capability authorizes the storage operation. Confusing those layers produces two common debugging traps: broadening CORS when signing is wrong, or changing signatures when a preflight response is incomplete.

Failure testing should cover an expired grant before transfer, expiration during the intended workflow, a retried part, duplicate completion, an aborted upload, a missing object, and a user who lost access after a link was issued. The last case exposes a real trade-off: a signed download remains a capability until its expiry. Sensitive records may require shorter download lifetimes because storage cannot perform a new application authorization check on each use of an already issued URL.

Observe the decision points. Log a correlation identifier, tenant identifier, opaque file identifier, operation, outcome, and expiry duration, but do not log the signed query string. Measure signing failures, upload completion time, part retries, abandoned multipart sessions, validation failures, and download authorization denials. Alerting on byte volume alone misses the delivery gaps that users actually feel.

## 5. Roll out with a capability matrix and reversible data movement

Evaluate candidates against a compact matrix built from the workflow: private objects by default, expiring signed uploads and downloads, multipart initiation and abort behavior, browser CORS control, checksum or integrity handling, lifecycle cleanup, auditability, and the operational limits revealed by load tests. S3 API compatibility narrows integration work, but it does not prove identical behavior for every edge case. **Compatibility must be demonstrated by the application's contract tests.**

| Test | Decision signal |
| --- | --- |
| Interrupt and resume a large upload | Only failed work must be retried |
| Leave a multipart session unfinished | Parts can be found and cleaned up |
| Use the deployed browser origin | Preflight and transfer both succeed |
| Reuse an expired download capability | Access is rejected |
| Remove a resident's application access | No new download capability is issued |

Start with one noncritical property cohort. Dual-write metadata only if migration requires it; avoid duplicating object bytes until the rollback and reconciliation plan is clear. Confirm that newly uploaded objects can be authorized, validated, downloaded, expired, and deleted, then increase traffic while watching completion latency and abandoned sessions.

The final choice is the implementation that passes those tests at the required concurrency and file sizes while the team can operate its failure modes. Keep price in the matrix, but do not let an attractive unit rate outrank correct private access, recoverable multipart uploads, or predictable egress behavior. That is the practical definition of simple for this system.
